# Plan: Faisabilité Intégration Membrane (getmembrane.com) dans Croo

## Résumé Exécutif

Membrane (anciennement integration.app) est une plateforme d'intégration "agentic" qui gère nativement le multi-tenant et le OAuth. Elle permet de remplacer le code custom actuel pour MS365 (Azure app, Graph API, delta sync, webhooks) et d'ajouter rapidement HubSpot et d'autres intégrations sans écrire de connecteurs.

**Verdict**: Faisable. Architecture recommandée : **un seul Workspace Membrane**, avec des **Tenants Membrane** dynamiques mappés aux entités Croo (`user_id`, `org_id`, ou `tenant_id` selon la configuration admin). Membrane gère l'OAuth, le refresh, le proxy API. Croo garde la persistence des emails, l'UI Inbox, et la logique métier.

## 1. Architecture Actuelle de Croo (Codebase)

### Hiérarchie d'entités
- **Tenant** (`tenant.model.ts`): Niveau supérieur. Équivalent à un "customer" SaaS. Contient plusieurs users, organizations, etc.
- **Organization** (`organization.model.ts`): Au sein d'un tenant. Liée aux contacts, opportunités, activités.
- **User** (`user.model.ts`): Utilisateur individuel avec `active_organization_id`.

### Intégration Email MS365 Actuelle
**Localisation** : `apis/exposed/communication-b4f-api/app/presentation/routes/ms365_routes.py`

**Flux** :
1. `GET /api/v1/ms365/auth-url` → backend génère URL OAuth2 MS Graph avec `state=current_user["user_id"]`
2. User redirigé vers Microsoft → callback `GET /api/v1/ms365/callback`
3. Backend échange `code` contre tokens, fetch profile, génère system JWT, appelle `email-backend-api` pour stocker la connection
4. Table `ms365_connections` (entity: `ms365_connection.py`): `user_id` unique, `access_token`, `refresh_token`, `email_delta_token`, `calendar_delta_token`, webhook subscriptions
5. `POST /api/v1/ms365/sync` → background task qui fait delta sync via `MS365GraphService`
6. `GET /api/v1/ms365/emails` → proxy vers `email-backend-api` qui liste les `synced_email` stockés
7. `POST /api/v1/ms365/emails/send` → backend appelle MS Graph API directement

**Problèmes identifiés** :
- Code custom complexe (393 lignes `ms365_graph_service.py` + 496 lignes `ms365_routes.py` + sync service + webhook handling)
- Un seul provider supporté (MS365 via Azure app)
- Delta tokens, webhooks, refresh tokens gérés manuellement
- Scaling limité à MS365

## 2. Architecture Membrane (Recherche Web)

### Concepts Clés
- **Organization** (Membrane): Niveau supérieur billing/access control. Regroupe les workspaces.
- **Workspace**: Environnement d'exécution où vivent les intégrations, connections, tenant data. Configuré une seule fois pour toute l'app.
- **Tenant/Customer** (Membrane): Unité d'isolation au sein d'un workspace. Chaque tenant a ses propres connections OAuth, credentials, activity logs. **Créé automatiquement** quand un nouveau `tenantKey` est vu dans un JWT.
- **Integration**: Configuration d'un connecteur pour un app externe (ex: Outlook, HubSpot). Définie au niveau workspace.
- **Connection**: Container de credentials pour un tenant spécifique vers une app externe. **Toujours tenant-level**.
- **Action**: Opération single-shot (ex: send email, create contact). Peut être Universal (cross-app), Integration-level, ou Connection-level.
- **Flow**: Workflow multi-étapes (ex: sync data, webhook handler).
- **Events**: Webhooks entrants ou polling de Membrane vers votre backend.

### Authentification
Token JWT signé par le backend Croo avec `workspaceKey` (iss) + `tenantKey` (id du tenant Membrane). Ex:
```javascript
const token = jwt.sign(
  { workspaceKey: process.env.MEMBRANE_WORKSPACE_KEY, tenantKey: 'user-123', name: 'John' },
  process.env.MEMBRANE_WORKSPACE_SECRET,
  { expiresIn: 7200, algorithm: 'HS512' }
)
```
Source: https://docs.getmembrane.com/docs/how-membrane-works/tenants

### Multi-tenancy dans Membrane
- "One tenant per end-user or organization. The most common pattern — each customer of your product is a separate tenant with their own OAuth connections."
- "Tenants are created automatically when someone authenticates with a new `tenantKey` in their JWT token."
- "Every connection belongs to exactly one tenant. When a tenant authenticates and connects an external app, the resulting connection is scoped to that tenant alone."
- Isolation enforce au niveau DB.

### Workspace Provisioning API
Membrane expose une API `POST /org-workspaces` pour créer des workspaces programmatiquement. "Useful for multi-tenant SaaS platforms that need to provision isolated integration environments for their own customers."
Source: https://docs.getmembrane.com/reference/Workspace%20Provisioning

## 3. Question Clé : "Chaque Tenant Croo a son propre compte Membrane"

### Option A : Un Workspace Membrane, multiples Tenants Membrane (RECOMMANDÉ)

**Mapping** :
- 1 Workspace Membrane = Toute l'application Croo
- Les Tenants Membrane sont créés dynamiquement par JWT (`tenantKey`)
- Billing: "Per-customer usage fee" facturé par Membrane selon le nombre de tenants actifs
- Configurations d'intégration (connecteurs, actions) partagées à tous les tenants Croo
- Isolation des données (connections, credentials) par tenant Membrane

**Avantages** :
- Simple à gérer, une seule configuration d'intégrations
- Pas de provisioning complexe
- Pricing prévisible (capped per customer)
- Natif à Membrane, supporté par la doc

**Inconvénient** :
- Pas d'isolation complète des configurations (tous les tenants Croo voient les mêmes intégrations disponibles)

### Option B : Un Workspace Membrane par Tenant Croo

**Mapping** :
- Chaque Tenant Croo se voit provisionner un Workspace Membrane via l'API `POST /org-workspaces`
- Chaque workspace a son propre `workspaceKey`/`workspaceSecret`
- Isolation complète des configurations

**Avantages** :
- Isolation maximale
- Chaque tenant Croo peut avoir des intégrations custom

**Inconvénients** :
- Complexité opérationnelle énorme (provisionner, gérer, rotater secrets pour N workspaces)
- Le pricing Membrane est "per-customer" (tenant), pas "per-workspace". Cela ne réduit pas le coût.
- Overkill pour la plupart des SaaS. L'API Workspace Provisioning est conçue pour les cas où une isolation totale est nécessaire (ex: enterprise self-hosting).

### Recommandation
**Option A**. Vos tenants Croo sont mappés comme des **Tenants Membrane**, pas comme des Workspaces Membrane. La distinction dans Membrane est:
- **Workspace** = votre produit (Croo)
- **Tenant/Customer** = les utilisateurs/organisations de votre produit

Si un jour un client Enterprise demande une isolation totale, vous pouvez provisionner un workspace dédié pour ce client spécifique.

## 4. Per-User vs Per-Organization

### Comment Membrane le supporte
Membrane est agnostique à ce que représente un `tenantKey`. C'est **votre backend** qui décide.

```python
# Configuration dans Croo: table integration_tenant_settings
# integration_key | tenant_id | scope_mode | scope_entity
# "outlook"       | "tenant-1"| "per-user" | "user"
# "hubspot"       | "tenant-1"| "per-org"  | "organization"
```

### Génération du JWT Membrane
```python
def generate_membrane_token(croo_user: User, integration_key: str):
    scope = get_integration_scope(croo_user.tenant_id, integration_key)
    
    if scope == "per-user":
        tenant_key = croo_user.id  # ex: "user-abc-123"
    elif scope == "per-organization":
        tenant_key = croo_user.active_organization_id  # ex: "org-xyz-456"
    elif scope == "per-tenant":
        tenant_key = croo_user.tenant_id  # ex: "tenant-acme"
    
    return jwt.sign(
        payload={
            "workspaceKey": MEMBRANE_WORKSPACE_KEY,
            "tenantKey": tenant_key,
            "name": croo_user.email,
            "fields": {
                "croo_user_id": croo_user.id,
                "croo_tenant_id": croo_user.tenant_id,
                "croo_org_id": croo_user.active_organization_id,
            }
        },
        key=MEMBRANE_WORKSPACE_SECRET,
        algorithm="HS512",
        expires_in="2h"
    )
```

### Implications
- **Per-user** (ex: Email Outlook): Chaque user a sa propre connection OAuth. Les emails sont privés à l'utilisateur.
- **Per-organization** (ex: HubSpot CRM): Toute l'org partage la même connection HubSpot. Les deals/contacts sont visibles à tous les membres de l'org.
- **Per-tenant** (ex: Slack workspace): Tout le tenant partage la même connection.

### UI Frontend
Le frontend appelle `/api/membrane-token?integration=outlook` avant d'ouvrir le popup de connexion Membrane. Le backend choisit le `tenantKey` approprié.

## 5. Approche Recommandée : Option A (OAuth + Proxy API)

Membrane gère ce que vous faites mal aujourd'hui. Croo garde ce qui est unique à votre produit.

### Ce que Membrane gère (remplace le code custom)
| Actuel (Croo custom) | Avec Membrane |
|---------------------|---------------|
| `ms365_graph_service.py` (393 lignes) | Connector Outlook pré-built dans Membrane |
| OAuth2 flow + callback + state | `membrane.ui.connect({ integrationKey: 'microsoft-outlook' })` |
| Token refresh + expiration | Auto-managed par Membrane |
| Delta sync emails + webhooks | Flow Membrane avec event subscription |
| Send/Reply/Forward via Graph API | Universal Action `send-email` via API Membrane |
| HubSpot connector (inexistant) | Connector HubSpot pré-built |

### Ce que Croo garde (valeur ajoutée)
| Fonction | Rationale |
|----------|-----------|
| UI Inbox (`frontend/src/app/pages/inbox`) | Expérience utilisateur custom |
| Stockage `synced_email` / `synced_event` | Indexation, recherche, linking contacts/organizations |
| Logique AI Insights | LLM parsing spécifique à Croo |
| Linking emails → contacts/orgs | Logique métier CASL/pipeline |
| Table `integration_settings` | Config per-user/per-org par tenant |

### Flux Email Migré
```
1. User clique "Connect Outlook" dans Settings
2. Frontend appelle GET /api/membrane-token?integration=outlook
3. Backend génère JWT avec tenantKey=user_id (car config=per-user)
4. Frontend appelle membrane.ui.connect({ integrationKey: 'microsoft-outlook' })
5. Popup OAuth Membrane → Microsoft → User autorise
6. Membrane stocke la connection (access_token, refresh, etc.)
7. Flow Membrane (configuré dans Console) écoute les nouveaux emails
8. Flow envoie webhook POST https://croo.app/api/v1/membrane/webhooks/email
9. Backend Croo reçoit le payload, upsert dans `synced_email` table
10. User voit les emails dans Inbox (depuis DB Croo, comme aujourd'hui)
11. User clique "Send" → Frontend appelle POST /api/v1/membrane/actions/send-email/run
    → Backend forward à Membrane API avec le JWT
    → Membrane appelle MS Graph API avec le bon token
```

## 6. Phases de Migration

### Phase 0 : Setup Membrane (1-2 jours)
- Créer un compte Membrane, configurer le Workspace
- Ajouter l'intégration Microsoft Outlook dans la Console Membrane
- Configurer l'OAuth app (ou utiliser l'OAuth app built-in de Membrane)
- Documenter le `workspaceKey` et `workspaceSecret`
- Ajouter les variables d'environnement à Croo

### Phase 1 : Token Generation + Connection UI (2-3 jours)
- Backend: Créer endpoint `GET /api/membrane-token` qui génère le JWT signé
- Frontend: Intégrer `<MembraneProvider>` avec `fetchToken` vers le backend
- Frontend: Remplacer le bouton "Connect MS365" par `membrane.ui.connect({ integrationKey: 'microsoft-outlook' })`
- Backend: Créer table `integration_settings` (tenant_id, integration_key, scope_mode)
- Admin UI: Permettre aux admins de choisir "per-user" ou "per-organization" par intégration

### Phase 2 : Proxy API (2-3 jours)
- Backend: Créer service `MembraneService` qui appelle l'API Membrane REST
- Remplacer `sendEmail`, `replyEmail`, `forwardEmail` pour passer par Membrane au lieu de Graph API
- Remplacer `getConnection` pour utiliser `GET /connections` via Membrane API
- Supprimer `ms365_graph_service.py` (ou le garder en fallback pendant la transition)

### Phase 3 : Sync Migration (3-5 jours)
- Console Membrane: Créer un Flow qui souscrit aux events "new email" et "new calendar event"
- Flow step 1: Recevoir l'event de Outlook
- Flow step 2: `api-request-to-your-app` → POST vers `https://croo.app/api/v1/membrane/webhooks/email`
- Backend: Créer endpoint webhook qui reçoit les emails/events et les upsert dans la DB
- Tester le delta sync vs le sync Membrane
- Migrer les données historiques si nécessaire

### Phase 4 : HubSpot + Nouvelles Intégrations (1-2 jours chacune)
- Console Membrane: Ajouter l'intégration HubSpot
- Configurer scope_mode "per-organization" dans Croo
- Frontend: Le bouton "Connect HubSpot" apparaît automatiquement via `useIntegrations()`
- Backend: Utiliser les Universal Actions Membrane pour "create-deal", "create-contact"
- Répéter pour Slack, Google Calendar, etc.

### Phase 5 : Cleanup (1 jour)
- Supprimer `ms365_graph_service.py`
- Supprimer les tables de webhook subscription custom
- Archiver les routes `/api/v1/ms365/auth-url`, `/api/v1/ms365/callback` (ou les rediriger vers Membrane)
- Mettre à jour la documentation

## 7. Risques et Considérations

### Risque 1 : Dépendance à un tier
Membrane est un SaaS externe. Si le service est down, les intégrations ne fonctionnent pas.
**Mitigation** : Membrane offre du self-hosting en add-on (Business Plan). Vous pouvez aussi garder un fallback vers votre Graph Service pendant la transition.

### Risque 2 : Format des données
Les payloads webhook de Membrane peuvent différer de votre format `synced_email` actuel.
**Mitigation** : Mapper/transformer les données dans votre endpoint webhook. Ne pas supprimer vos tables existantes.

### Risque 3 : Pricing
Membrane facture "per active customer" + "usage fee" (action runs, AI credits).
Source: https://getmembrane.com/pricing
- Plan Business: "Capped usage fee per customer", "Self-hosting add-on"
- Le pricing a des caps: "Pay for what you use, never more than the ceiling."
**Action** : Estimer le nombre d'utilisateurs actifs et le volume d'emails pour obtenir un devis Membrane.

### Risque 4 : Migration des connections existantes
Les users déjà connectés à MS365 doivent re-autoriser via Membrane (nouveau OAuth flow).
**Mitigation** : Migration transparente: détecter les connections existantes, afficher un banner "Reconnect via notre nouveau système d'intégration".

### Risque 5 : Per-tenant workspace
Si vous insistez pour un workspace par tenant Croo, la complexité devient exponentielle (N workspaces à provisionner, monitorer, payer).
**Recommandation** : Ne pas faire ça sauf besoin enterprise absolu.
